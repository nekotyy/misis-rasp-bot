# Готовый промпт для разработки миниаппа

Скопируй текст ниже в задачу разработки в репозитории `misis-rasp-bot`. Подробные архитектурные решения и критерии приёмки находятся в [miniapp-development-plan.md](miniapp-development-plan.md). Этот документ — задание на будущую реализацию, а не описание уже работающей функции.

---

Разработай Telegram Mini App и VK Mini App для существующего проекта `misis-rasp-bot`. Нужен рабочий продукт на реальных данных с полноценной интеграцией с текущими Telegram/VK-ботами.

## Цель и стек

Сделай единый мобильный фронтенд: React + TypeScript + Vite, Tailwind CSS + shadcn/ui, TanStack Query, React Router и Lucide. Используй актуальные совместимые стабильные версии и закрепи lock-файл. Бэкенд — FastAPI на Python текущего проекта. Сохрани SQLite, Alembic, действующий парсер, планировщик, RabbitMQ и доставку уведомлений.

Оформи интерфейс современно: чистые поверхности, выразительные карточки пар, аккуратные скругления, хороший контраст, спокойный акцент, плавные короткие переходы и skeleton-загрузка. Приоритет — скорость, читаемость русских названий предметов и удобство одной рукой. Сделай светлую, тёмную и системную тему, поддержку safe area, увеличения текста и reduced motion. Все основные действия должны быть доступны без жестов. Нижняя навигация с иконками и подписями: «Расписание», «История», «Профиль».

## Перед изменениями

Прочитай применимые AGENTS.md и `docs/miniapp-development-plan.md`. Исследуй код через ast-index, обновив индекс при необходимости. Найди все пути чтения и записи подписок/настроек из Telegram, VK и админки, текущие правила выбора источника, подгрупп, замен и доставки. Следуй проектным правилам тестов, commit и push.

Подготовь короткую карту интеграции и затем последовательно реализуй этапы. Не переписывай ботов целиком. Сохрани текущие сценарии, полезные кнопки, fallback, авторизацию и безопасность админки. Не удаляй runtime и рабочие данные.

## Вкладка 1 — «Расписание»

1. При открытии загружай профиль и основную подписку из общей БД бота. Существующему пользователю не нужно заново выбирать его группу.
2. Поддержи несколько подписок на группы: одна основная и переключатель между остальными. Выбранная для просмотра группа и основная группа — разные состояния; просмотр не должен незаметно менять основную подписку.
3. Показывай сегодня, завтра и послезавтра с точными датами и днями недели. По умолчанию открыт сегодняшний день. Не подменяй отсутствующий день следующим найденным расписанием.
4. Карточка пары содержит номер, предмет, преподавателя, кабинет. Время добавляй только из достоверного расписания звонков.
5. Изменённые пары выделяй отдельным фоном, значком и текстовой меткой; раскрытие показывает «Было → Стало». Различай замену предмета, преподавателя, кабинета, добавление и подтверждённую отмену.
6. Сопоставляй пары корректно при одинаковых номерах и подгруппах; не используй номер как единственный уникальный ключ. При неоднозначности не выдумывай соответствие старой и новой пары.
7. Храни опорную ревизию для визуальных изменений отдельно от обновляемого baseline рассылки. Отметка замены не должна исчезать сразу после отправки ботом уведомления. Правило опоры: первая принятая версия даты, для сегодняшнего дня — первая принятая версия дня. Если опоры нет, показывай обычное расписание без ложных меток.
8. Переиспользуй реальные принятые снимки из сайта, ручного ввода и OCR, приоритеты источников, фильтрацию вузовских недель/подгрупп и защиту от ложных пустых ответов сайта. Совпадение данных с ботом проверяй при одинаковой группе, дате и подгруппе.
9. Показывай время обновления, происхождение и устаревание данных. Различай «пар нет», «не опубликовано», «данные устарели», «ошибка сети» и «нет подписки».
10. Обновляй данные после возврата в приложение, смены группы и явного обновления. API не запускает парсинг или рассылку на каждое чтение.

## Вкладка 2 — «История»

1. Показывай итоговое известное расписание прошедших дней выбранной группы за последние три календарных месяца. Сегодняшние и будущие занятия не называй пройденными.
2. Основная навигация — по неделям. Кнопки: «Предыдущая неделя», «Следующая неделя», «К последней неделе»; также выбор даты. Сверху отображай период недели.
3. Дни внутри недели идут от новых к старым. Пример для открытия 4 ноября 2026 года: «Вторник, 3 ноября 2026 года», «Понедельник, 2 ноября 2026 года». День раскрывается в итоговый список пар с учётом замен. Сохраняй группу, неделю и позицию прокрутки при переключении вкладок.
4. Обеспечь обратную совместимость: при первом развёртывании выполни безопасный backfill из уже существующих `schedule_snapshots`, чтобы доступные прошлые дни отображались сразу. Для каждого источника и даты выбирай последнюю достоверную версию, а не просто последний общий снимок. Отсутствие даты в более новом снимке не удаляет старый день.
5. При необходимости используй другие сохранённые источники только когда они достоверно содержат полный состав дня. Не восстанавливай расписание из агрегированного счётчика и не выдавай повторяющееся недельное расписание за доказанное прошлое с заменами.
6. Не дублируй один день из-за нескольких снимков. Подтверждённый пустой день показывай как «Пар не было», отсутствие записи — «Расписание за этот день не сохранилось». Покажи доступный период архива.
7. Backfill должен быть идемпотентным, возобновляемым, выполняться до очистки нужных старых снимков и не запускать рассылки или пересчёт пройденных пар.
8. Новые принятые снимки обновляют дневной архив. Более поздняя явная корректировка прошлого дня обновляет итог с отметкой времени исправления. Полный журнал внутридневных версий в MVP не нужен.
9. Храни архив достаточно долго для трёх календарных месяцев; действующее удаление старых снимков через 90 дней само по себе не гарантирует этот срок. Границы периода и недели вычисляй в `APP_TIMEZONE`, корректно обрабатывай месяцы разной длины.
10. Проверяй архив на тестовой старой БД. Не обращайся к рабочим персональным данным без необходимости. Не обещай восстановление дней, исходные данные которых не сохранились.

## Вкладка 3 — «Профиль»

1. Показывай профиль текущей платформы: имя, доступный аватар, Telegram/VK и ссылки; после связывания — обе платформы.
2. Покажи все подписки на группы, выбор основной, добавление из существующего каталога и отписку от конкретной группы.
3. Подтверждай отписку с названием группы. После связывания объясняй, что изменение действует для общего аккаунта и обоих ботов. Если удаляется основная группа, предложи другую или оставь понятное состояние без подписки.
4. Добавь общий переключатель уведомлений, выбор связанных каналов доставки и настройки для группы. Сначала проверь фактическую семантику существующего флага `homework_notifications_enabled`; UI должен честно соответствовать реально работающим рассылкам.
5. Раздели предпочтения пользователя и доступность канала: блокировка Telegram не выключает VK. Чтение миниаппа не снимает автоматически ограничения доставки. Отказ в разрешениях платформы не выглядит как успешно включённая доставка.
6. Кастомизация MVP: системная/светлая/тёмная тема, небольшой набор акцентов, компактный/обычный режим, уменьшение анимации. Сохраняй общие настройки на сервере.
7. Не переноси Telegram file ID стикера в VK. Существующую платформенную персонализацию сохрани совместимой и отображай отдельно, если она доступна.

## Общий аккаунт и связь Telegram ↔ VK

Связывание добровольное. До него Telegram и VK остаются отдельными аккаунтами. После него подписки, основная группа и общие настройки едины; изменение в любом из ботов или миниаппе видно в остальных каналах.

Используй внутренний account ID и уникальные identity `(platform, user_id)`. Существующие записи `users` не удаляй. Введи безопасные совместимые миграции и общий сервис операций. Старые поля основной подписки допускаются как транзакционно обновляемая проекция, но не как независимый источник истины. Выбор группы в старом боте меняет основную подписку, не удаляя дополнительные группы миниаппа.

Сценарий связывания: авторизованная первая платформа создаёт одноразовую короткоживущую ссылку, пользователь открывает её во второй платформе, сервер проверяет авторизацию второй стороны и показывает оба профиля и расхождения. После явного подтверждения атомарно объединяются данные. Для разных основных групп/настроек дай выбор. Обрабатывай уже связанный аккаунт, конкурирующие подтверждения, истечение и повторное использование секрета. Не связывай по username, имени, фото или совпадению числовых ID. Не переноси admin/editor-права между платформами. Добавь безопасную отвязку с понятной судьбой подписок, настроек и сессий.

Обнови разрешение активных источников и получателей уведомлений для нескольких групп. Повторная задача и связь двух платформ не должны удваивать доставку одному получателю в одном канале. Существующие подписки на преподавателей/кабинеты не преобразовывай автоматически в групповые: сохрани их и предоставь понятный переход в бот, если их UI пока не реализован.

## Платформы, авторизация и деплой

- Telegram: официальный WebApp API, серверная проверка исходного `initData`, подписи и свежести `auth_date`. Не доверяй `initDataUnsafe` для авторизации.
- VK: официальный VK Bridge и серверная проверка подписанных параметров запуска с app ID и временем. Имя/аватар из Bridge не заменяют доказательство личности.
- Реализуй `PlatformAdapter`: определение окружения, запуск, тема, safe area, «Назад», ссылки и optional haptics. Проверяй доступность методов; отказы Bridge обрабатывай явно.
- Выдавай короткую отзывную сессию миниаппа; токен держи в памяти фронтенда, не в постоянном browser storage. Не смешивай её с admin-сессией. После истечения — штатный повторный вход.
- Все операции проверяют владельца по сессии, а не по переданному клиентом user ID. Ограничь auth/link-запросы по частоте, не логируй секреты или параметры запуска.
- Подними отдельное публичное FastAPI-приложение и nginx/HTTPS-маршруты. Не ослабляй login guard, cookie policy, ограничения docs, CSP и прочие правила админки. Настрой iframe-политику миниаппа под текущие требования VK/TG отдельно.
- UI и API одного миниаппа желательно разместить на одном origin. Scheduler и рассылка продолжают жить в существующем процессе. Сборка фронтенда воспроизводима и включена в CI.
- Сохрани действующие клавиатуры ботов и добавь штатные кнопки открытия миниаппа. Development-режим с тестовыми профилями допускается только при явном локальном включении и не должен работать в production.

## Этапы работы

1. Аудит и контракты: карта интеграции, DTO, правила архива/замен, экраны и состояния.
2. Архив: миграция, backfill старых дней, обновление из всех принятых источников, политика хранения.
3. Общие аккаунты и подписки: совместимость старых пользователей, единый сервис записи и доставка для нескольких групп.
4. Проверка Telegram/VK-запуска, сессии и API профиля/расписания/истории/настроек.
5. React-оболочка, адаптеры, нижнее меню, темы и обработка ошибок.
6. Реальные расписание и история с недельной навигацией.
7. Профиль, настройки, связывание, конфликты и отвязка.
8. Сквозные тесты, smoke в обоих клиентах, Docker/nginx/CI и документация.

После каждого законченного этапа выполняй применимые проверки и делай подробный Conventional Commit на русском языке от первого лица в прошедшем времени, затем push в настроенную ветку `development`, согласно AGENTS.md. Не останавливайся на макете или фиктивных данных: готовность оценивается по полному сценарию.

## Проверки и критерии готовности

Напиши backend-тесты в `tests/` на новую логику. Покрой старую БД, повторный backfill, точные даты, актуальную версию дня, пропуски, отмены, 3 календарных месяца, разные подгруппы и повторяющиеся номера пар. Проверь сохранение отметки замены после рассылки.

Покрой подписи и сессии, чужие подписки, безопасное связывание с подтверждением обеих сторон, конфликты и одноразовость секрета. Проверь обновление основной группы и настроек из каждого канала, несколько групп, дедупликацию рассылки, разделение блокировки канала и общих предпочтений.

Для фронтенда проверь пользовательские состояния через Vitest/Testing Library и основные переходы через Playwright. Проведи smoke в реальных Telegram/VK на мобильном устройстве и desktop: safe area, «Назад», темы, недоступные методы, отсутствие сети, восстановление сессии и история старых дней. Не называй проверку моков проверкой реальной интеграции.

Перед коммитом обязательно:

```powershell
uv run --frozen ruff check src web_configurator tests scripts --output-format=github
uv run --frozen python -m compileall -q src web_configurator tests scripts
uv run --frozen python -m unittest discover -s tests -p "test_*.py" -v
```

Добавь новые Python-каталоги в проверки, когда они появятся. После изменения деплоя выполни `docker compose config`; для фронтенда — typecheck, tests, production build. Если Docker недоступен из Windows, проверь WSL. Не останавливай чужие контейнеры.

Обнови README, `.env.example`, инструкции настройки приложений Telegram/VK, HTTPS, резервного копирования и первого запуска с backfill. Не добавляй реальные секреты в репозиторий. Предусмотри отключение миниаппа без потери данных и без остановки ботов.

Готовый результат: существующий пользователь открывает приложение из своего бота, сразу видит свою группу и три дня, узнаёт замены по карточкам, переходит в прошлые недели с доступными старыми данными, управляет уведомлениями и подписками, при желании связывает Telegram/VK и получает синхронное состояние во всех каналах.

В итоговом отчёте перечисли реализованные сценарии, выполненные проверки, commit/push и конкретные внешние настройки, которые ещё нужны для запуска. Не отмечай реализацию завершённой, если остались заглушки ключевых функций.
