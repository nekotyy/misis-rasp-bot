# MISIS Schedule Bot

Асинхронный бот расписания для колледжа МИСИС с поддержкой Telegram, VK, RabbitMQ и веб-дашборда для администрирования.

## Что умеет проект

- показывает расписание по группам, преподавателям и аудиториям;
- хранит пользователей и их подписки в SQLite;
- отслеживает изменения расписания и рассылает уведомления;
- умеет работать с RabbitMQ, но не умирает без него: остается direct fallback;
- считает пройденные пары по группам и дисциплинам;
- поднимает веб-дашборд для метрик, управления счетчиками и администрирования;
- поддерживает массовые и тестовые рассылки из вебки.

## Архитектура

Проект состоит из четырех основных частей:

1. `src/` — основная логика бота, парсер, планировщик, доставка, БД.
2. `web_configurator/` — FastAPI-дашборд и веб-авторизация.
3. `runtime/` — рабочие данные в Docker: SQLite, JSON счетчиков, вложения.
4. `deploy/nginx/` — шаблон nginx для публичного доступа к дашборду.

Поток данных выглядит так:

1. Пользователь пишет в Telegram или VK.
2. Бот сохраняет или обновляет пользователя в `users`.
3. Парсер забирает расписание с сайта колледжа.
4. Снимки расписания пишутся в `schedule_snapshots`.
5. При изменении создается запись в `change_events`.
6. Уведомления отправляются либо через RabbitMQ, либо напрямую.
7. Если включены счетчики пар, ночная задача учитывает прошедшие пары и пишет события в `lesson_counter_events`.

## Хранилища данных

### SQLite

Основная база проекта — SQLite. По умолчанию используется `bot.db`, в Docker — `runtime/bot.db`.

Ключевые таблицы:

- `users` — TG/VK-пользователи, подписки, флаги админа/редактора;
- `schedule_snapshots` — снимки расписания;
- `change_events` — журнал изменений;
- `delivery_events` — история доставки сообщений;
- `lesson_counters` — настроенные счетчики пар;
- `lesson_counter_events` — учтенные пары;
- `web_users` — пользователи веб-дашборда.

### JSON

JSON теперь остается только там, где он действительно удобен:

- `storage/lesson_counters.json` или `runtime/lesson_counters.json` — конфигурация счетчиков пар;
- `storage/web_users.json` может использоваться только как legacy-источник для одноразового импорта веб-пользователей в SQLite.

## Безопасность веб-пользователей

Короткий ответ: хранить веб-пользователей в JSON можно только как временный компромисс, но для прода лучше БД.

Что было раньше:

- логины и права лежали в `storage/web_users.json`;
- пароли хранились не в открытом виде, а в PBKDF2-HMAC-SHA256 хешах;
- то есть это не была катастрофа, но это все равно менее надежно операционно.

Почему SQLite лучше:

- один источник истины вместе с основной БД проекта;
- атомарные обновления без риска битого JSON;
- проще бэкапить и переносить;
- легче сопровождать в Docker и на VPS;
- нет отдельного runtime-файла с критичными учетками;
- меньше шанс случайно потерять права или словить гонку записи.

Сейчас веб-пользователи хранятся в таблице `web_users` в SQLite. Старый JSON при наличии можно один раз импортировать через `WEB_USERS_JSON_IMPORT_PATH`.

1. Скопировать пример окружения:

```bash
cp .env.example .env
```

2. Заполнить `.env`.

3. Установить зависимости:

```bash
uv sync --frozen
```

4. Запустить бота:

```bash
uv run --frozen -m src.main
```

5. Запустить веб-дашборд:

```bash
uv run --frozen uvicorn web_configurator.app:app --host 0.0.0.0 --port 8080
```

## Как работает бот

### Telegram и VK

Оба бота работают параллельно, но независимо друг от друга:

- Telegram стартует только если задан `TELEGRAM_BOT_TOKEN`;
- VK стартует только если задан `VK_BOT_TOKEN`;
- падение одного канала не должно останавливать второй.

`src/main.py` поднимает для каждого канала supervisor-задачу с перезапуском при падении.

### Парсинг расписания

Основной парсер живет в `src/parser.py`.

Что делает:

- загружает HTML расписания;
- превращает его в структуру дней и пар;
- нормализует данные;
- считает хеш снимка;
- отдает snapshot для БД и сравнения.

### Изменения расписания

Фоновый планировщик:

- сохраняет baseline;
- делает текущий парс;
- сравнивает текущий снимок с baseline;
- пишет изменения в БД;
- создает рассылку подписчикам.

### Подсчет пар

Счетчики задаются по группам:

- группа;
- дисциплина;
- преподаватель;
- сколько прошло;
- сколько всего.

Поддерживается:

- карточный редактор в вебке;
- raw JSON-режим;
- валидация по реальному расписанию группы;
- ночной учет прошедших пар;
- защита от дублей через `lesson_counter_events`.

## Техническая документация

### Жизненный цикл приложения

Точка входа проекта — `src/main.py`.

При старте происходит такой bootstrap:

1. Загружается `.env` через `Settings.from_env()`.
2. Применяются миграции Alembic.
3. Инициализируется SQLite-схема через `Database.initialize()`.
4. Загружается каталог групп.
5. Создаются:
   - `ScheduleParser`
   - `ScheduleSearchCatalog`
   - `LessonCounterService`
   - `RabbitMQBroker`
   - `LessonCounterJobBroker`
   - `Broadcaster`
6. Отдельно стартуют Telegram и VK polling-петли.
7. Стартует consumer уведомлений RabbitMQ.
8. Стартует APScheduler с фоновыми задачами.
9. Выполняется начальный `sync_current_snapshot()`.

Важная деталь: Telegram, VK, RabbitMQ-consumer и lesson-counter consumer стартуют независимо. Если один кусок лег, остальные не обязаны падать вместе с ним.

### Механизм парса расписания

Основной модуль — `src/parser.py`, класс `ScheduleParser`.

#### Источник данных

Парсер работает с HTML-страницами расписания колледжа. Базовый URL задается через `SCHEDULE_URL`.

Если `SCHEDULE_URL=http://asu.sf-misis.ru/rasp/600`, то парсер:

- отрезает конечный numeric segment;
- использует базу `http://asu.sf-misis.ru/rasp`;
- собирает итоговый URL группы как `/rasp/{schedule_id}`.

#### Загрузка HTML

Методы:

- `fetch_html(schedule_id)` — загрузка по `schedule_id`;
- `fetch_html_from_url(url)` — загрузка по прямому URL;
- `_get_with_retry()` — HTTP GET с retry и backoff.

Поведение retry:

- используется `httpx.AsyncClient`;
- по умолчанию до `3` попыток;
- между попытками — линейный backoff;
- ошибки логируются, последняя ошибка пробрасывается наверх.

#### Разбор HTML

`parse_html()` делает следующее:

1. Ищет заголовок группы в `div#titleF`.
2. Ищет блоки дней через `div.titleDate`.
3. Для каждого дня берет соседний `div.rasp`.
4. Достает строки таблицы с парами.
5. Для каждой строки извлекает:
   - номер пары,
   - предмет,
   - преподавателя,
   - аудиторию.
6. Собирает `ScheduleSnapshot`, который содержит:
   - `group_name`
   - `fetched_at`
   - список `DaySchedule`

#### Нормализация даты

Дата из человекочитаемой подписи превращается в `YYYY-MM-DD` через внутреннюю карту месяцев.

#### Хеширование снимка

После парса вызывается `compute_hash(snapshot)`.

Хеш строится из:

- имени группы;
- ISO-даты каждого дня;
- списка пар в порядке номера;
- полей `number`, `subject`, `teacher`, `classroom`.

Итог — SHA-256. Он нужен, чтобы:

- быстро понимать, изменился ли снимок;
- дедуплицировать change events;
- не рассылать одно и то же изменение повторно.

### Каталог групп и поисковые сущности

`src/group_catalog.py` отвечает за массовую загрузку каталога групп и маппинг:

- `group_name -> schedule_id`
- `schedule_id -> group_name`

`src/schedule_search.py` расширяет это на:

- преподавателей;
- аудитории;
- унифицированный поиск по тексту пользователя.

Это используется как в боте, так и в веб-валидации счетчиков.

### Как работает сравнение изменений

Фоновые задачи не сравнивают HTML напрямую. Они сравнивают структурированные snapshots.

Сценарий:

1. Берется baseline из `schedule_snapshots`.
2. Делается новый current parse.
3. `ScheduleComparator.compare()` сравнивает:
   - даты;
   - наличие/отсутствие пар;
   - содержимое конкретной пары.
4. Если отличий нет, работа на этом заканчивается.
5. Если отличия есть:
   - строится `change_summary`;
   - в БД пишется `change_events`;
   - в `Broadcaster` отправляется текст уведомления;
   - baseline обновляется до нового состояния.

Именно поэтому проект умеет жить в режиме “снимок -> сравнение -> событие”, а не в режиме “каждый раз тупо отправить все расписание заново”.

### Планировщик APScheduler

Фоновые задачи живут в `src/scheduler.py`, класс `ScheduleJobs`.

По умолчанию регистрируются:

- `save_daily_baseline` в `00:00`
- `save_daily_baseline_fallback` в `05:00`
- `sync_current_snapshot` каждый час в `:10`
- дополнительный `sync_current_snapshot` в учебное окно `09:40`-`13:40`
- `count_today_lessons` в `23:00` и `23:40`, если включены счетчики

#### Почему две baseline-задачи

- `00:00` — штатный baseline на день;
- `05:00` — fallback, если ночью что-то сорвалось.

#### Почему два запуска счетчиков пар

- `23:00` — основной учет прошедших пар;
- `23:40` — перепроверка, если расписание/доступность источника менялись.

#### Защита от гонок

Внутри `ScheduleJobs` есть отдельные `asyncio.Lock`:

- `_sync_lock`
- `_baseline_lock`
- `_lesson_counter_lock`

Если задача уже идет, вторая копия пропускается. Это защищает от наложений и двойного учета.

### Работа RabbitMQ

В проекте RabbitMQ используется для двух независимых потоков:

1. очередь уведомлений пользователям;
2. очередь задач подсчета пар.

#### Брокер уведомлений

`src/message_broker.py`:

- `OutboundMessage` — полезная нагрузка сообщения;
- `RabbitMQBroker` — producer + consumer для уведомлений.

Поля `OutboundMessage`:

- `platform`
- `user_id`
- `text`
- `campaign_type`
- `attempt`
- `max_attempts`
- `message_id`

#### Публикация уведомления

Когда `Broadcaster` хочет отправить сообщение, он сначала пробует:

1. собрать `OutboundMessage`;
2. опубликовать его в durable queue;
3. если publish не удался — откатиться в direct send.

То есть RabbitMQ здесь ускоряет и стабилизирует доставку, но не является единственным способом отправки.

#### Consumer уведомлений

Consumer:

- читает JSON из очереди;
- десериализует в `OutboundMessage`;
- вызывает `Broadcaster.deliver(payload)`;
- по успеху делает `ack`.

Если доставка упала:

- пока `attempt < max_attempts`, создается retry payload;
- retry повторно публикуется в очередь;
- исходное сообщение `ack`-ается, чтобы не плодить дубль;
- если retry publish сам сломался, делается `nack(requeue=True)`;
- если попытки исчерпаны, сообщение `reject(requeue=False)`.

Это дает контролируемый retry без бесконечной зацикленной доставки.

#### Брокер задач счетчиков

Для счетчиков есть отдельный класс `LessonCounterJobBroker` и отдельная очередь.

Payload:

- `schedule_id`
- `attempt`
- `max_attempts`
- `job_id`

Это позволяет:

- не мешать заданиям подсчета с обычными пользовательскими уведомлениями;
- повторять конкретный job отдельно;
- ограничить `prefetch_count` для более аккуратной фоновой обработки.

### Direct fallback без RabbitMQ

Если `RABBITMQ_URL` пустой или RabbitMQ временно недоступен:

- `Broadcaster` не ломается;
- publish возвращает `False`;
- бот вызывает `_send_telegram()` или `_send_vk()` напрямую.

Это важно для продовой отказоустойчивости: очередь полезна, но не делает проект неживым без себя.

### Как работает доставка сообщений

Основной модуль — `src/notifier.py`, класс `Broadcaster`.

Он умеет:

- рассылать обычные уведомления о расписании;
- рассылать админские широковещательные сообщения;
- отправлять сообщения администраторам;
- писать delivery telemetry в БД.

#### Telegram

При отправке в Telegram:

- вызывается `bot.send_message()`;
- при успехе пишется `delivery_events(status='sent')`;
- при ошибке пишется `delivery_events(status='failed')`.

Дополнительно для Telegram есть автоотключение недоставляемых пользователей:

- блокировка бота пользователем;
- `chat not found`;
- `user is deactivated`;
- другие постоянные ошибки.

Такие пользователи помечаются как `delivery_disabled_auto=1`, чтобы бот не бился в них бесконечно.

#### VK

Для VK логика похожая, но без отдельной авто-деактивации по типу Telegram permanent failure.

### Схема БД по смыслу

#### `users`

Хранит:

- платформу;
- user_id;
- username/full_name;
- тип подписки;
- ключ подписки;
- название подписки;
- URL подписки;
- группу;
- schedule_id;
- флаги `is_admin`, `is_editor`;
- флаги доставки.

#### `schedule_snapshots`

Хранит структурированные снимки расписания:

- baseline;
- current.

#### `change_events`

Хранит журнал изменений:

- источник;
- хеш снимка;
- итоговый текст изменения;
- список затронутых дат;
- payload для дальнейшего использования.

#### `delivery_events`

Хранит телеметрию доставки:

- кампания;
- платформа;
- через broker или direct;
- успех/ошибка;
- номер попытки;
- текст ошибки.

#### `lesson_counters`

Хранит конфигурацию прогресса:

- группа;
- предмет;
- преподаватель;
- нормализованные ключи;
- сколько прошло;
- сколько всего.

#### `lesson_counter_events`

Хранит факт конкретного учтенного занятия. Таблица нужна для идемпотентности: одна и та же пара не должна увеличивать счетчик дважды.

#### `web_users`

Хранит логины веб-дашборда, хеши паролей и права.

### Механизм счетчиков пар

`src/lesson_counters.py` работает поверх snapshots расписания.

Общий сценарий:

1. Конфиг грузится из JSON.
2. Конфиг синхронизируется в `lesson_counters`.
3. Ночью для каждой настроенной группы делается parse.
4. Для сегодняшнего дня выбираются пары.
5. Каждая пара матчится по:
   - нормализованному предмету;
   - преподавателю;
   - группе.
6. Если совпадение найдено и такого события еще не было, пишется `lesson_counter_events`.
7. У соответствующего счетчика увеличивается `passed_count`.

Именно `lesson_counter_events` защищает от повторного учета при повторном ночном запуске.

### Веб-дашборд как клиент к БД

Вебка не живет в отдельной бизнес-логике. Она в основном:

- читает SQLite;
- валидирует пользовательские действия;
- вызывает существующие сервисы проекта;
- показывает срез состояния.

Это хорошо тем, что:

- меньше дублирования;
- одна и та же бизнес-логика используется и ботом, и вебкой;
- меньше шансов, что вебка и бот “понимают” проект по-разному.

### Миграции и совместимость

Есть два уровня эволюции схемы:

1. Alembic-мigrations;
2. defensive `CREATE TABLE IF NOT EXISTS` и `_ensure_column()` в `Database.initialize()`.

Такая схема выбрана, чтобы проект:

- уверенно поднимался на чистой машине;
- не ломался на старой продовой базе;
- переживал постепенное расширение таблиц без ручной возни.

### Сценарии отказа

#### Падает Telegram

- Telegram supervisor перезапустит polling;
- VK и вебка продолжают жить.

#### Падает VK

- VK supervisor перезапустит polling;
- Telegram и вебка продолжают жить.

#### Падает RabbitMQ

- consumer может не подняться;
- direct fallback остается;
- планировщик и основной бот не обязаны падать.

#### Падает вебка

- бот и очереди продолжают работать;
- теряется только web UI.

#### Битый legacy JSON веб-пользователей

- импорт просто пропускается;
- основным источником остается SQLite;
- суперпользователь из `.env` все равно может войти.

### Текущий технологический профиль проекта

Если совсем коротко, проект — это:

- async Python service;
- polling-боты Telegram и VK;
- HTML parser;
- event journal;
- delivery pipeline с queue/fallback;
- admin dashboard на FastAPI;
- SQLite как основное рабочее хранилище.

## Веб-дашборд

Веб-модуль расположен в `web_configurator/` и запускается на FastAPI + Uvicorn.

Основные разделы:

1. `Метрики`
2. `Счетчики пар`
3. `Управление ботом`
4. `Веб-пользователи`

### Что показывает дашборд

- аптайм;
- общее число пользователей;
- разбивку TG/VK;
- новых и старых пользователей;
- подписки на преподавателей и группы;
- тихих пользователей;
- статус Telegram / VK / RabbitMQ;
- последний парс расписания;
- последнее изменение расписания;
- журнал последних изменений;
- активные группы и число пользователей в них;
- доставку сообщений за сегодня и за все время;
- состояние счетчиков пар.

## Права веб-пользователей

Права выдаются точечно.

- `stats_overview` — верхние карточки и общая сводка.
- `stats_users` — список TG/VK-пользователей и фильтры.
- `stats_services` — статус Telegram, VK и RabbitMQ.
- `stats_schedule` — парсинг, активные группы, журнал изменений.
- `stats_delivery` — доставка сообщений.
- `stats_lesson_counters` — метрики счетчиков пар.
- `config_lesson_counters` — редактирование счетчиков.
- `manage_bot_admin` — рассылки и служебные действия из вебки.
- `manage_web_users` — управление веб-аккаунтами и их правами.

Суперпользователь из `.env` всегда имеет все права и не хранится как обычная запись в таблице `web_users`.

## Что делает `Управление ботом`

Раздел в вебке позволяет:

- отправить общую рассылку;
- отправить тестовую рассылку;
- форсировать перепарс активных источников;
- сохранить актуальный baseline вручную.

Рассылки ставятся в очередь через RabbitMQ. Если брокер недоступен, основная логика доставки в самом боте остается с direct fallback, но веб-операции управления ожидают рабочий маршрут доставки.

## Админка внутри ботов

Кроме вебки, часть управления остается внутри Telegram/VK-админки:

- просмотр статуса;
- поиск пользователей;
- кликабельные ID и профили;
- управление редакторами;
- внутренние админские сценарии каналов.

## Валидация счетчиков пар

В `web_configurator/lesson_editor.py` конфиг проверяется по реальному расписанию:

- существует ли группа;
- существует ли дисциплина в расписании;
- можно ли нормализовать название дисциплины;
- соответствует ли преподаватель записи в расписании;
- не битая ли структура JSON.

Это позволяет избежать ситуации, когда в конфиг попадает `"информатика"`, а на сайте `"Информатика"` или `"Информатика."`.

## Надежность и отказоустойчивость

Что уже заложено в проект:

- Telegram и VK стартуют независимо;
- есть supervisor-циклы с перезапуском;
- RabbitMQ не является единственной точкой отказа для основной доставки;
- бот может жить без одного из каналов;
- вебка вынесена отдельно от логики самого бота;
- счетчики пар ведутся через отдельную очередь и отдельный журнал событий.

## Что важно при деплое

1. Не потерять старую БД.
2. Убедиться, что Docker смотрит именно в `runtime/bot.db`.
3. Если раньше веб-пользователи жили в JSON, оставить путь в `WEB_USERS_JSON_IMPORT_PATH` на первый старт.
4. Проверить доступность внешнего `80/tcp` перед выпуском сертификата.
5. После certbot перезапустить `nginx`.

## Рекомендации по прод-эксплуатации

- держать `runtime/` на постоянном диске;
- регулярно бэкапить `runtime/bot.db`;
- не хранить суперпароль вебки как `change-me`;
- ограничить доступ к RabbitMQ management UI;
- не использовать legacy JSON как постоянное хранилище веб-пользователей;
- после переноса на SQLite считать JSON только миграционным хвостом.
