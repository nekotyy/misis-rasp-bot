# План полного переноса на Rust

Этот документ — рабочая инструкция по переносу всего приложения, включая Telegram, VK, планировщик, веб-админку, Mini App API и клиент, импорт расписания и эксплуатационные инструменты. Цель — сохранить существующие сценарии и данные и запустить систему на VPS с **1 vCPU, 1 ГБ ОЗУ, 10 ГБ NVMe, портом 50 Мбит/с и лимитом исходящего трафика 0,5 ТБ**. Числа на скриншоте — характеристики тарифа, а не измеренная доступная приложению память: ОС, nginx, мониторинг и другие сервисы тоже потребляют ресурсы.

Рабочая ветка: `codex/rust-rewrite`. Существующие Python-сервисы остаются эталоном поведения до подтверждённого переключения. План — не свидетельство завершения миграции. До начала следующего крупного этапа получить актуальные `origin/development` и `origin/main`, изучить новые коммиты и перенести нужные исправления в рабочую ветку; не переписывать историю этих веток. В частности, после начала переноса в `development` появились исправления очереди и `parse_mode`: их необходимо отдельно сверить и учесть в Rust и тестах. Коммит `1e28253` также существенно изменяет `tests/test_miniapp_api.py` (diff показывает замену многострочного файла одной строкой); перед объединением проверить, что тесты Mini App по-прежнему обнаруживаются и запускаются, не отбрасывая исходное покрытие автоматически.

## Текущее состояние

- В `rust/` есть библиотека `misis-rasp-core`, а не готовый исполняемый сервис. Production продолжает работать на Python.
- Уже имеются модели и сериализация расписания, загрузка и разбор колледжа и университета, каталоги, поиск и его предпросмотр, подгруппы, сравнение изменений, SQLite-схема новой базы, часть операций пользователей и аккаунтов, архивные проекции, основа синхронизации и outbox, HTTP-транспорт Telegram/VK, основы long poll и часть сценариев Telegram.
- Транзакционная обработка уже перенесённых Telegram-событий связывает изменение данных, постановку ответа в outbox и отметку обработки; неподдержанные события не подтверждаются. Добавляются групповые команды с проверкой администратора. Это не полный Telegram-бот.
- Последние исправления `development` пока **не включены**: в Python ожидание обновления снимка ограничено 3 секундами при любом сохранённом снимке и 6 секундами без него, при ошибке возвращается сохранённый снимок; для доставки введены конечные попытки и обработка слишком большой сущности. Текущие Rust-пути необходимо привести к этим условиям и отдельно проверить, чтобы не блокировать очередь. Явную передачу `parse_mode` проверить во всех отправках и редактированиях.
- У VK пока есть транспорт, дедупликация и основы long poll; обработчики пользовательских сценариев не перенесены. Для админки реализована только совместимость хешей паролей; её веб-сервер, Mini App API, планировщик, OCR и приложение запуска отсутствуют.
- `rust/schema.sql` отражает Python-схему после миграции `20261105_0007`. Инициализация Rust принимает пустую БД либо существующую БД этой версии с ожидаемыми таблицами, полями и уникальными индексами. Автоматических миграций старых версий и переключения production пока нет.
- Последний замер на старом VPS был разовым: около 372 МиБ у бота, 76 МиБ у RabbitMQ и 502 МиБ у проектных сервисов вместе; `runtime` около 2,3 ГиБ, в том числе резервные копии около 1,2 ГиБ, файлы outbox около 568 МиБ и SQLite около 378 МиБ. Нагрузку, свободную память и состав файлов нужно измерить повторно перед переездом; другие сервисы сервера тоже используют ресурсы. Данные и кэш Docker автоматически не удалялись.

## Архитектура и зависимости

Ориентир — один Rust-бинарник с явными режимами `bot`, `web`, `miniapp-api`, служебными командами и общим ядром. Режимы позволяют сначала запускать части раздельно и сохранить границы процессов; объединение в один процесс допустимо только после измерений и проверки изоляции отказов. Веб-клиент и nginx обслуживаются отдельно. На финальном этапе выбрать число контейнеров по фактическому RSS и эксплуатационным требованиям, а не предполагать выигрыш без замеров.

Использовать уже закреплённые в `rust/Cargo.toml` `serde`/`serde_json`, `tokio`, `reqwest` с `rustls`, `scraper`, `rusqlite` с bundled SQLite, `chrono`/`chrono-tz`, `regex`, `unicode-normalization`, `unicode-casefold`, `sha2`, `pbkdf2`, `base64`, `subtle`, `getrandom` и `dotenvy`. Перед добавлением новых зависимостей проверить документацию, лицензию, поддерживаемые версии Rust, граф зависимостей и размер release-сборки; версии фиксировать `Cargo.lock`.

Рекомендуемые кандидаты, требующие проверки на этапе внедрения:

| Задача | Кандидат и граница применения |
| --- | --- |
| HTTP API | `axum` + `tower`/`tower-http`; маршруты и middleware должны воспроизвести текущие контракты и ограничения безопасности, а не просто заменить FastAPI. |
| Асинхронные задачи | `tokio` с ограниченной конкурентностью; календарные задания строить по `chrono-tz` и тестировать DST. Не создавать отдельный поток на каждого пользователя. |
| SQLite | Оставить `rusqlite`, выполнять блокирующие обращения вне async-исполнителя, использовать короткие транзакции, WAL и ограниченное число соединений. Не смешивать параллельные записи без явной стратегии. |
| HTTP и боты | Существующий `reqwest`-транспорт; добавлять SDK только если он сохраняет обработку ошибок, ограничения запросов и совместимость payload. Токены не логировать. |
| Подписи и авторизация | `hmac`, `sha2`, `subtle`, `base64`, `getrandom`; совместимость формата существующих токенов и сроков проверять тестами. Готовые JWT-библиотеки применять только к реально используемому формату. |
| Наблюдаемость | `tracing`/`tracing-subscriber`, при необходимости `metrics`/экспортёр; ограничить объём логов и не включать секреты и персональные данные. |
| RabbitMQ | Оценить `lapin` либо совместимый AMQP-клиент. Замена брокера SQLite-outbox допустима лишь после доказательства эквивалентной надёжности всех видов заданий и поэтапного вывода сообщений. |
| Шаблоны админки | Изучить текущие HTML/CSS и выбрать `askama` либо сохранение статических шаблонов с безопасной подстановкой; обеспечить HTML-экранирование и те же формы. |
| Тестирование | Встроенные `cargo test`, `tokio::test`, локальные HTTP-заглушки, при необходимости `proptest` для форматов и `tower::ServiceExt` для HTTP; тесты не должны требовать настоящих токенов или production. |
| Клиент Mini App | Изучить `miniapp_frontend/` и сохранить внешний вид и API. Если переносить клиентскую логику на Rust, оценить `leptos`/Wasm и итоговый размер загрузки; HTML, CSS и статические ресурсы сохраняют свою роль. Выбор подтверждается сборкой, проверкой Telegram/VK WebView и замером трафика, а не только языком. |
| OCR и Gemini | Сначала описать фактический протокол `gemini_webapi`, входы/выходы и управление cookies. Подобрать поддерживаемый Rust-клиент или реализовать совместимый адаптер только после проверки возможностей и условий доступа; отдельный лёгкий процесс допустим, если это уменьшает постоянную память. Нельзя объявлять OCR перенесённым по одной заглушке. |

Новые имена модулей ниже — целевая структура, а не утверждение, что файлы уже существуют. `rust/src/lib.rs` и будущий `rust/src/main.rs` остаются точками сборки; при необходимости вынести подсистемы в отдельные crates только после появления реальной пользы для сборки или изоляции.

Первичные справочники для реализации: [axum: маршруты, состояние и middleware](https://docs.rs/axum/latest/axum/), [Tokio: задачи и блокирующий код](https://docs.rs/tokio/latest/tokio/), [rusqlite: API SQLite и backup](https://docs.rs/rusqlite/latest/rusqlite/), [руководство Leptos, включая WebAssembly и взаимодействие с JavaScript](https://book.leptos.dev/). Версии в этих ссылках могут меняться; фактически используемые версии определяет lock-файл проекта.

## Пошаговое исполнение и готовые компоненты

Общий принцип: сначала искать поддерживаемую библиотеку с нужными функциями, затем делать небольшой адаптер под контракты проекта. Не писать собственные HTTP-фреймворк, AMQP-клиент, криптографию, SQL-движок, парсер HTML или планировщик с нуля. Уже написанные Rust-компоненты сохранять, пока замена готовой библиотекой не доказала совместимость и не усложнила миграцию; в первую очередь рассмотреть готовые решения для ещё не перенесённых частей. Перед внедрением проверять актуальность API, лицензию, поддержку и цену по памяти/размеру; используемые версии фиксировать lock-файлом.

### Фаза 0 — как выполнять

1. `git fetch --all --prune`, сравнить `origin/development` с рабочей веткой и выписать изменения, влияющие на Rust-контракты. Отдельно проверить количество обнаруживаемых тестов Mini App до и после интеграции.
2. Создать в `docs/` таблицу инвентаризации: путь Python, функция/маршрут/событие, вход, результат, проверки прав, побочные эффекты, Rust-модуль и тест. Указывать **не перенесено**, **в работе**, **проверено**; не считать ручную сверку завершением всех тестов.
3. Копировать SQLite штатным backup API SQLite через [rusqlite backup](https://docs.rs/rusqlite/latest/rusqlite/) с включённой соответствующей feature; проверять `PRAGMA integrity_check` и реальное восстановление на отдельном стенде. Не копировать работающую базу простым копированием одного файла без учёта WAL.
4. Собрать исходные метрики штатными Docker/Linux-инструментами и существующей `web_configurator/metrics.py`; не разрабатывать отдельный мониторинг до понимания пробелов. Записать дату и условия измерения в журнал.

### Фаза 8 — как выполнять

1. Использовать готовый официальный образ Rust как builder и минимальный runtime-образ с необходимыми CA-сертификатами и часовыми поясами; не создавать собственную систему сборки. Фиксировать версии образов, собирать `--locked` и проверять зависимости бинарника и запуск TLS/SQLite.
2. Выключать ненужные default features библиотек после тестирования, сравнивать release-сборки с `strip`, LTO и разным числом codegen units. Взвесить время сборки и риск превышения памяти; сборку вынести в CI.
3. Запускать нагрузочный стенд с ограничениями контейнеров: измерять RSS и пики на старте/опросе/OCR, время ответов, число запросов и рост файлов. Проверять не только среднее, но и одновременную работу ОС, nginx, брокера и резервного копирования.
4. Кэширование и сжатие настраивать готовыми средствами `reqwest`, HTTP-сервера и nginx, только если это не нарушает свежесть расписания. Зафиксировать фактические результаты и изменить конфигурацию по измерениям.

### Фаза 9 — как выполнять

1. В существующие GitHub Actions добавить стандартные команды Cargo и сборку тестового образа; использовать готовый BuildKit/multi-stage Docker и не помещать `runtime` и секреты в build context.
2. Добавить smoke-тесты compose: создание чистой БД, запуск режимов, health endpoint, mock Telegram/VK, завершение и повторный старт. Отдельно воспроизвести обновление с копии поддерживаемой старой БД.
3. Протестировать теневую сверку без внешней отправки и изменения production, затем последовательное переключение с подтверждённой резервной копией. Проверить восстановление и возврат к старому образу на отдельном стенде.
4. Вести журнал развёртывания и замеров, обновлять документацию и конфигурацию; удалять Python-зависимости только после закрытия всех матриц функций, безопасности и эксплуатационных тестов.

## Команды и порядок работы

Из корня рабочей ветки:

```powershell
git status --short
git fetch --all --prune
cargo fmt --manifest-path rust/Cargo.toml -- --check
cargo clippy --locked --manifest-path rust/Cargo.toml --all-targets -- -D warnings
cargo test --locked --manifest-path rust/Cargo.toml
uv run --frozen ruff check src web_configurator tests scripts --output-format=github
uv run --frozen python -m compileall -q src web_configurator tests scripts
uv run --frozen python -m unittest discover -s tests -p "test_*.py" -v
```

Для изменений Docker, окружения и deployment дополнительно выполнить `docker compose config`; если Docker не найден в Windows, проверить WSL. На машине разработки Rust с bundled SQLite требует рабочего C-компилятора: при его отсутствии в Windows использовать настроенный Rust в WSL и отдельный `CARGO_TARGET_DIR` вне дерева проекта. Для веба дополнительно проверять вход и ограничения безопасности; для ботов — клавиатуры, ошибки и fallback. Не создавать тестовую нагрузку на настоящий сайт, сервер или пользователей без необходимости.

После каждого логически завершённого и проверенного объёма обновлять статусы в этом документе и [журнал переноса](rust-migration-log.md): фиксировать, что сделано, как работает, зачем, чем проверено и что осталось. Затем делать подробный Conventional Commit на русском языке и отправлять рабочую ветку. Фазы не считать завершёнными по подготовительным модулям; продолжать работу до закрытия всех критериев или сообщать о конкретном непреодолимом препятствии.
