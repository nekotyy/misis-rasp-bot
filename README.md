# MISIS Schedule Bot

Асинхронный бот расписания для колледжа МИСИС с поддержкой Telegram, VK, RabbitMQ и веб-дашборда для администрирования.

## Что умеет проект

- показывает расписание по группам, преподавателям и аудиториям;
- хранит пользователей и их подписки в SQLite;
- отслеживает изменения расписания и рассылает уведомления;
- умеет работать с RabbitMQ, но не умирает без него: остается direct fallback;
- считает пройденные пары по группам и дисциплинам;
- поднимает веб-дашборд для метрик, управления счетчиками и администрирования;
- поддерживает массовые и тестовые рассылки из вебки.

## Архитектура

Проект состоит из четырех основных частей:

1. `src/` — основная логика бота, парсер, планировщик, доставка, БД.
2. `web_configurator/` — FastAPI-дашборд и веб-авторизация.
3. `runtime/` — рабочие данные в Docker: SQLite, JSON счетчиков, вложения.
4. `deploy/nginx/` — шаблон nginx для публичного доступа к дашборду.

Поток данных выглядит так:

1. Пользователь пишет в Telegram или VK.
2. Бот сохраняет или обновляет пользователя в `users`.
3. Парсер забирает расписание с сайта колледжа.
4. Снимки расписания пишутся в `schedule_snapshots`.
5. При изменении создается запись в `change_events`.
6. Уведомления отправляются либо через RabbitMQ, либо напрямую.
7. Если включены счетчики пар, ночная задача учитывает прошедшие пары и пишет события в `lesson_counter_events`.

## Хранилища данных

### SQLite

Основная база проекта — SQLite. По умолчанию используется `bot.db`, в Docker — `runtime/bot.db`.

Ключевые таблицы:

- `users` — TG/VK-пользователи, подписки, флаги админа/редактора;
- `schedule_snapshots` — снимки расписания;
- `change_events` — журнал изменений;
- `delivery_events` — история доставки сообщений;
- `lesson_counters` — настроенные счетчики пар;
- `lesson_counter_events` — учтенные пары;
- `web_users` — пользователи веб-дашборда.

### JSON

JSON теперь остается только там, где он действительно удобен:

- `storage/lesson_counters.json` или `runtime/lesson_counters.json` — конфигурация счетчиков пар;
- `storage/web_users.json` может использоваться только как legacy-источник для одноразового импорта веб-пользователей в SQLite.

## Безопасность веб-пользователей

Короткий ответ: хранить веб-пользователей в JSON можно только как временный компромисс, но для прода лучше БД.

Что было раньше:

- логины и права лежали в `storage/web_users.json`;
- пароли хранились не в открытом виде, а в PBKDF2-HMAC-SHA256 хешах;
- то есть это не была катастрофа, но это все равно менее надежно операционно.

Почему SQLite лучше:

- один источник истины вместе с основной БД проекта;
- атомарные обновления без риска битого JSON;
- проще бэкапить и переносить;
- легче сопровождать в Docker и на VPS;
- нет отдельного runtime-файла с критичными учетками;
- меньше шанс случайно потерять права или словить гонку записи.

Сейчас веб-пользователи хранятся в таблице `web_users` в SQLite. Старый JSON при наличии можно один раз импортировать через `WEB_USERS_JSON_IMPORT_PATH`.

## Быстрый запуск локально

1. Скопировать пример окружения:

```bash
cp .env.example .env
```

2. Заполнить `.env`.

3. Установить зависимости:

```bash
uv sync --frozen
```

4. Запустить бота:

```bash
uv run --frozen -m src.main
```

5. Запустить веб-дашборд:

```bash
uv run --frozen uvicorn web_configurator.app:app --host 0.0.0.0 --port 8080
```

## Docker и деплой

Обычный запуск:

```bash
docker compose up -d --build
```

Поднимаются сервисы:

- `bot`
- `rabbitmq`
- `web`
- `nginx`

Что важно:

- если RabbitMQ недоступен, бот продолжает работать с direct fallback;
- если не задан один из токенов, соответствующий бот просто не стартует;
- если не поднялся веб, основной бот все равно может продолжать работать;
- основная рабочая БД в Docker лежит в `runtime/bot.db`.

### Nginx

Публичная схема такая:

- `http://dashboard.nekoty.ru` — HTTP на порту `80`
- `https://dashboard.nekoty.ru:2443` — HTTPS на порту `2443`

Nginx берет конфиг из:

- [deploy/nginx/default.conf.template](deploy/nginx/default.conf.template)

Внутри Docker трафик идет так:

```text
internet -> nginx -> web:8080
```

### Сертификаты

Контейнер nginx ожидает сертификаты в смонтированной директории:

```text
deploy/certs/live/dashboard.nekoty.ru/fullchain.pem
deploy/certs/live/dashboard.nekoty.ru/privkey.pem
```

После обновления сертификатов:

```bash
docker compose restart nginx
```

## Как работает бот

### Telegram и VK

Оба бота работают параллельно, но независимо друг от друга:

- Telegram стартует только если задан `TELEGRAM_BOT_TOKEN`;
- VK стартует только если задан `VK_BOT_TOKEN`;
- падение одного канала не должно останавливать второй.

`src/main.py` поднимает для каждого канала supervisor-задачу с перезапуском при падении.

### Парсинг расписания

Основной парсер живет в `src/parser.py`.

Что делает:

- загружает HTML расписания;
- превращает его в структуру дней и пар;
- нормализует данные;
- считает хеш снимка;
- отдает snapshot для БД и сравнения.

### Изменения расписания

Фоновый планировщик:

- сохраняет baseline;
- делает текущий парс;
- сравнивает текущий снимок с baseline;
- пишет изменения в БД;
- создает рассылку подписчикам.

### Подсчет пар

Счетчики задаются по группам:

- группа;
- дисциплина;
- преподаватель;
- сколько прошло;
- сколько всего.

Поддерживается:

- карточный редактор в вебке;
- raw JSON-режим;
- валидация по реальному расписанию группы;
- ночной учет прошедших пар;
- защита от дублей через `lesson_counter_events`.

## Веб-дашборд

Веб-модуль расположен в `web_configurator/` и запускается на FastAPI + Uvicorn.

Основные разделы:

1. `Метрики`
2. `Счетчики пар`
3. `Управление ботом`
4. `Веб-пользователи`

### Что показывает дашборд

- аптайм;
- общее число пользователей;
- разбивку TG/VK;
- новых и старых пользователей;
- подписки на преподавателей и группы;
- тихих пользователей;
- статус Telegram / VK / RabbitMQ;
- последний парс расписания;
- последнее изменение расписания;
- журнал последних изменений;
- активные группы и число пользователей в них;
- доставку сообщений за сегодня и за все время;
- состояние счетчиков пар.

## Права веб-пользователей

Права выдаются точечно.

- `stats_overview` — верхние карточки и общая сводка.
- `stats_users` — список TG/VK-пользователей и фильтры.
- `stats_services` — статус Telegram, VK и RabbitMQ.
- `stats_schedule` — парсинг, активные группы, журнал изменений.
- `stats_delivery` — доставка сообщений.
- `stats_lesson_counters` — метрики счетчиков пар.
- `config_lesson_counters` — редактирование счетчиков.
- `manage_bot_admin` — рассылки и служебные действия из вебки.
- `manage_web_users` — управление веб-аккаунтами и их правами.

Суперпользователь из `.env` всегда имеет все права и не хранится как обычная запись в таблице `web_users`.

## Роуты веб-дашборда

### HTML-страницы

- `GET /` — главная страница дашборда.
- `GET /login` — форма входа.
- `GET /lessons` — экран управления счетчиками пар.
- `GET /web-users` — экран управления веб-пользователями.
- `GET /control` — экран управления ботом.

### Аутентификация

- `POST /login` — вход в дашборд.
- `POST /logout` — выход из дашборда.

### Метрики

- `GET /api/metrics` — JSON с метриками, уже отфильтрованный по правам текущего пользователя.

### Счетчики пар

- `POST /lessons/json` — валидация и сохранение JSON-конфига.
- `POST /lessons/groups` — добавить группу.
- `POST /lessons/groups/delete` — удалить группу.
- `POST /lessons/subjects` — добавить или изменить дисциплину/преподавателя.
- `POST /lessons/subjects/delete` — удалить дисциплину.

### Веб-пользователи

- `POST /web-users` — создать пользователя или обновить пароль/права.
- `POST /web-users/delete` — удалить пользователя.

### Управление ботом

- `POST /control/broadcast` — массовая рассылка.
- `POST /control/test` — тестовая рассылка.
- `POST /control/refresh` — перепарсить активные источники.
- `POST /control/baseline` — сохранить baseline для активных источников.

## Что делает `Управление ботом`

Раздел в вебке позволяет:

- отправить общую рассылку;
- отправить тестовую рассылку;
- форсировать перепарс активных источников;
- сохранить актуальный baseline вручную.

Рассылки ставятся в очередь через RabbitMQ. Если брокер недоступен, основная логика доставки в самом боте остается с direct fallback, но веб-операции управления ожидают рабочий маршрут доставки.

## Админка внутри ботов

Кроме вебки, часть управления остается внутри Telegram/VK-админки:

- просмотр статуса;
- поиск пользователей;
- кликабельные ID и профили;
- управление редакторами;
- внутренние админские сценарии каналов.

## Валидация счетчиков пар

В `web_configurator/lesson_editor.py` конфиг проверяется по реальному расписанию:

- существует ли группа;
- существует ли дисциплина в расписании;
- можно ли нормализовать название дисциплины;
- соответствует ли преподаватель записи в расписании;
- не битая ли структура JSON.

Это позволяет избежать ситуации, когда в конфиг попадает `"информатика"`, а на сайте `"Информатика"` или `"Информатика."`.

## Надежность и отказоустойчивость

Что уже заложено в проект:

- Telegram и VK стартуют независимо;
- есть supervisor-циклы с перезапуском;
- RabbitMQ не является единственной точкой отказа для основной доставки;
- бот может жить без одного из каналов;
- вебка вынесена отдельно от логики самого бота;
- счетчики пар ведутся через отдельную очередь и отдельный журнал событий.

## Что важно при деплое

1. Не потерять старую БД.
2. Убедиться, что Docker смотрит именно в `runtime/bot.db`.
3. Если раньше веб-пользователи жили в JSON, оставить путь в `WEB_USERS_JSON_IMPORT_PATH` на первый старт.
4. Проверить доступность внешнего `80/tcp` перед выпуском сертификата.
5. После certbot перезапустить `nginx`.

## Рекомендации по прод-эксплуатации

- держать `runtime/` на постоянном диске;
- регулярно бэкапить `runtime/bot.db`;
- не хранить суперпароль вебки как `change-me`;
- ограничить доступ к RabbitMQ management UI;
- не использовать legacy JSON как постоянное хранилище веб-пользователей;
- после переноса на SQLite считать JSON только миграционным хвостом.
