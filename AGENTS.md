# AGENTS.md

Этот файл задает базовые правила для ИИ-агентов, которые работают с репозиторием `misis-rasp-bot`.

## 1. Что это за проект

`misis-rasp-bot` — это бот расписания для колледжа МИСИС с несколькими точками входа и собственной админкой.

Основные части проекта:
- `src/` — основная бизнес-логика, парсинг, планировщик, доставка уведомлений, работа с БД, Telegram и VK;
- `web_configurator/` — FastAPI-админка, веб-авторизация, security-логика, метрики;
- `tests/` — unit tests и smoke-level проверки;
- `scripts/` — служебные скрипты, в том числе генерация release notes;
- `deploy/nginx/` — nginx-шаблон для внешнего HTTPS-доступа;
- `runtime/` — рабочие данные контейнера: SQLite, JSON, вложения и временные runtime-файлы.

Технологии:
- Python 3.12+
- SQLite
- FastAPI
- aiogram
- vkbottle
- RabbitMQ
- Docker / Docker Compose
- nginx

## 2. Главные принципы изменений

Агент должен делать изменения так, чтобы:
- не ломать пользовательский UX в Telegram и VK;
- не ломать админку и логин в ней;
- не ослаблять защиту веб-интерфейса;
- не терять данные в `runtime/` и SQLite;
- не ухудшать деплой в Docker и поведение CI/CD;
- не вносить “косметические” массовые переделки без явной пользы.

Если задача не требует рефакторинга, предпочтительнее точечное исправление, а не широкая перестройка.

## 3. Как устроен рабочий поток

Базовый сценарий:
1. Изучить затронутые файлы и понять текущую логику.
2. Внести минимально достаточные изменения.
3. **Написать автоматический тест** в папке `tests/` для любой добавленной функции или изменения бизнес-логики.
4. Проверить код и прогнать полный набор тестов (`python -m unittest discover -s tests -p "test_*.py"`).
5. Обновить документацию или `.env.example`, если поведение реально изменилось.
6. Сделать понятный коммит.

Если есть несколько вариантов реализации, нужно предпочитать тот, который:
- проще сопровождать;
- меньше ломает существующее поведение;
- лучше соответствует уже принятому стилю проекта.

## 4. Git и ветки

Рабочие правила:
- по умолчанию работать в `development`, если пользователь не попросил иное;
- после каждого важного завершенного шага делать commit и push;
- commit message писать на русском языке, в форме “сделал / починил / добавил / настроил”;
- не делать `git reset --hard`, `git checkout --` и другое разрушительное переписывание без прямого запроса;
- не переписывать историю `main` или `development`;
- не откатывать чужие изменения только потому, что они кажутся лишними.

Если в рабочем дереве есть неожиданные правки, агент должен:
- понять, мешают ли они текущей задаче;
- не трогать их, если они не конфликтуют с работой;
- остановиться и уточнить у пользователя, только если конфликт прямой и опасный.

## 5. Версии, релизы и CI/CD

В проекте настроены автоматические workflow GitHub Actions.

Нужно помнить:
- CI запускается на `push` и на PR;
- Docker image публикуется автоматически через GitHub Actions;
- GitHub Release создается автоматически только после `push` в `main`;
- релиз создается по версии из `pyproject.toml`;
- если тег `vX.Y.Z` уже существует, новый release с той же версией не создастся;
- release notes генерируются автоматически скриптом `scripts/generate_release_notes.py`.

Правило для новых релизов:
- если нужен новый GitHub Release формата `vX.Y.Z`, перед merge в `main` нужно поднять `project.version`.

## 6. Что важно не сломать в UI и ботах

Для Telegram и VK важна консистентность поведения.

Нужно беречь:
- стартовые кнопки и навигацию;
- поиск расписания;
- кнопки возврата;
- уведомления об изменениях расписания;
- админские действия и массовые рассылки;
- тексты ошибок и подсказок для пользователя.

Особенно важно:
- если сообщение об изменениях расписания уже содержит полезные кнопки, нельзя их “случайно потерять”;
- тексты для пользователя желательно держать понятными и русскоязычными;
- новый UX в ботах должен быть совместим с текущими сценариями, а не только “красивым”.

## 7. Правила для веб-админки и безопасности

Веб-админка — чувствительная часть проекта. По умолчанию агент не должен ослаблять текущий hardening.

Нельзя без причины:
- отключать или ослаблять login guard / rate limit;
- убирать аудит попыток входа;
- ослаблять session cookie policy;
- открывать FastAPI docs наружу;
- публиковать админку напрямую в интернет без nginx / HTTPS;
- добавлять admin endpoints без проверки доступа.

Нужно помнить:
- `localhost`, `127.0.0.1` и `::1` должны оставаться удобными для локального запуска;
- внешний HTTP не считается безопасным режимом для админки;
- чувствительные действия должны быть защищены и проверяемы.

Если агент добавляет новую admin-функцию, он должен проверить:
- кто имеет к ней доступ;
- как она логируется;
- не ломает ли она текущие cookie/session/security настройки;
- нужен ли audit trail.

## 8. База данных и runtime-данные

Проект использует SQLite и runtime-файлы. Изменения, влияющие на состояние, нужно делать аккуратно.

Правила:
- не удалять и не очищать runtime-данные без явного запроса;
- не менять формат рабочих JSON/SQLite “между делом”;
- если добавляется новая таблица, поле или журнал, нужно подумать о совместимости;
- если изменение влияет на backup/restore, это нужно отметить в документации.

## 9. Когда нужно обновлять документацию

README, `.env.example` и сопутствующая документация должны отражать реальное поведение проекта.

Обновлять документацию нужно, если:
- добавились новые env-переменные;
- изменился процесс запуска или деплоя;
- изменилось поведение release / CI / Docker;
- появилась новая крупная админская функция;
- изменилось публичное поведение бота, которое пользователь должен понимать.

Не стоит править README ради стилистики, если задача к этому не относится.

## 10. Проверки перед сдачей

Минимальный набор проверок зависит от типа изменений.

**Правило по тестам:**
При добавлении любой новой функции или изменении логики агент **обязан** написать соответствующий unit/smoke тест в папке `tests/` и убедиться в его успешном прохождении перед коммитом в GitHub.

Обычно перед сдачей нужно прогонять:
- `python -m compileall src web_configurator tests scripts`
- `python -m unittest discover -s tests -p "test_*.py" -v`

Если менялись Docker, env, workflow или деплой:
- `docker compose config`

Если менялась веб-админка:
- проверить локальный вход;
- проверить, что security-ограничения не сломали `localhost`;
- проверить, что ошибки логина и блокировки ведут себя ожидаемо.

Если менялись уведомления и боты:
- проверить клавиатуры;
- проверить fallback-сценарии;
- проверить, что сообщения остаются читаемыми.

## 11. Что считается хорошим результатом

Хороший результат для этого репозитория — это изменение, которое:
- решает задачу без лишнего шума;
- не ломает уже работающие каналы;
- не ухудшает безопасность;
- не оставляет проект в “полупереходном” состоянии;
- сопровождается понятным commit message;
- при необходимости отражено в документации и проверках.

## 12. Короткий чеклист для новой задачи

Перед завершением полезно быстро пройтись по вопросам:
- что именно изменилось для пользователя;
- что изменилось для админа;
- есть ли риск для Telegram, VK, web admin или Docker;
- нужна ли новая env-переменная;
- нужна ли правка README или `.env.example`;
- нужны ли тесты или smoke-проверка;
- не задело ли это релизы, CI/CD или security.

## 13. Практическое правило для агента

Если есть сомнение между “сделать быстро” и “сделать безопасно и предсказуемо”, для этого проекта нужно выбирать второе.
