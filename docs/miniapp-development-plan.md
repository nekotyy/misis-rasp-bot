# План Telegram Mini App и VK Mini App

Статус: выполнен первоначальный аудит интеграции; реализация миниаппа ещё не начата. Основано на коде ветки `development` и требованиях пользователя от 4 ноября 2026 года.

Готовый промпт для реализации: [miniapp-development-prompt.md](miniapp-development-prompt.md).

Карта существующих путей и черновые контракты: [miniapp-integration-audit.md](miniapp-integration-audit.md).

## 1. Согласованное поведение

- Один React-фронтенд для Telegram и VK с адаптерами платформ; FastAPI-бэкенд поверх бизнес-логики существующего бота.
- Нижняя навигация: **Расписание · История · Профиль**.
- Основная группа берётся из подписки в боте. В миниаппе есть основная группа и переключатель между подписками.
- Telegram и VK можно добровольно связать в один аккаунт. После связывания группа, подписки и пользовательские настройки общие; изменения из любого бота тоже синхронизируются.
- Расписание показывает сегодня, завтра и послезавтра. Это три календарных дня, включая выходные; дни без опубликованных данных не подменяются другими датами.
- Замены выделяются фоном, маркером и текстом с объяснением изменения.
- История показывает итоговое известное расписание каждого прошедшего дня за три календарных месяца с навигацией по неделям. Полная лента версий внутри дня в MVP не нужна.
- При первом запуске история заполняется из уже сохранённых данных проекта, а не начинается с даты установки миниаппа.
- Профиль показывает пользователя Telegram/VK, связанные платформы, подписки, уведомления и оформление; позволяет отписаться от выбранной группы.

## 2. Что уже есть и что нужно добавить

| Область | Текущее состояние | Работа для миниаппа |
| --- | --- | --- |
| Пользователи | `src/models.py:UserRecord`, ключ `(platform, user_id)` | Общий аккаунт и связи с существующими пользователями без потери данных |
| Подписки | `Database.set_user_subscription`, одна основная подписка; есть отдельная подписка на кабинет | Несколько подписок на группы, одна основная; кабинет не считать второй группой |
| Данные расписания | `ScheduleSnapshot`, `DaySchedule`, `Lesson` | JSON DTO для UI с происхождением, актуальностью и деталями замен |
| Выбор даты | `get_day_by_offset`, `get_day_by_offset_from_content` | Сохранить точное соответствие календарной дате |
| Применение расписания | `ScheduleJobs.apply_snapshot`, `apply_manual_snapshot` | Общий путь принятия данных и обновления архива; чтение API не запускает рассылку |
| Источники | Сайт, ручной/OCR-импорт; есть вузовские недели и подгруппы | Сохранить приоритеты и фильтрацию, не вводить второй парсер |
| Изменения | `ScheduleComparator`, снимки `current` / `daily_baseline`, `change_events` | Структурированный diff по парам. Текущий компаратор формирует сообщения по дням, а не готовые статусы каждой карточки |
| Базовая версия | `daily_baseline` обновляется и после обработки изменений | Отдельно сохранять опорную ревизию для визуальных замен: сравнение с текущим baseline после рассылки может уже не показать изменение |
| История | `schedule_snapshots` хранит версии; есть счётчики пар | Построить архив по датам из версий; агрегированные счётчики не заменяют состав пар за день |
| Очистка | `Database.cleanup_old_records(days=90)` удаляет старые снимки | Хранить дневной архив минимум три календарных месяца; 90 дней не всегда достаточно |
| Уведомления | `homework_notifications_enabled`, `delivery_disabled_auto`, действующая доставка | Проверить фактическую семантику флага, выделить общие предпочтения и отдельную доступность каналов |
| Персонализация | Например, Telegram `custom_sticker_file_id` | Добавить оформление миниаппа; платформенные ресурсы оставить в своей платформе |
| Веб | FastAPI-админка и nginx | Отдельное публичное FastAPI-приложение миниаппа с собственной пользовательской авторизацией |

Это точки интеграции, а не обещание, что нужные API или таблицы уже существуют. Полнота архива рабочей БД пока не проверялась.

## 3. Стек и устройство

Предлагаемый фронтенд: **React + TypeScript + Vite**, **Tailwind CSS + shadcn/ui**, **TanStack Query**, **React Router**, **Lucide**. Даты форматировать через `Intl` с русской локалью; календарные вычисления вынести в проверенные утилиты. Использовать системный шрифт с кириллицей. Дополнительную библиотеку анимаций подключать только при реальной необходимости: для MVP достаточно CSS-переходов.

Один набор компонентов обеспечивает одинаковые сценарии в двух платформах. Адаптеры Telegram WebApp API и VK Bridge отвечают за запуск, параметры авторизации, тему, safe area, кнопку «Назад», ссылки и доступные тактильные отклики. Возможности проверяются перед вызовом; отсутствие haptics или аватара не блокирует приложение. UI-kit не считается автоматически одобренным платформой: требования VK проверяются перед публикацией.

Бэкенд: Python текущего проекта, FastAPI, Pydantic DTO, существующий `Database` / aiosqlite, Alembic. SQLite и RabbitMQ сохраняются. Новая БД и Redis для MVP не требуются. Конкретные версии JS-зависимостей выбрать по совместимости на старте и закрепить lock-файлом.

Поток данных:

```text
Сайт / ручной импорт / OCR
            ↓
Существующее принятие и проверка снимка
            ↓
SQLite: снимки + дневной архив + метаданные замен
            ↓
Общие сервисы расписания / аккаунта / подписок
        ↙             ↓              ↘
 Telegram-бот      FastAPI API       VK-бот
                       ↓
                 React Mini App
                  ↙         ↘
            Telegram        VK Bridge
```

Предлагаемые новые каталоги: `miniapp_frontend/`, `miniapp_api/`; общие сервисы размещать в `src/`. Статику и API публиковать через nginx по HTTPS, желательно на отдельном origin миниаппа. Админские сессии и публичные пользовательские сессии разделены. Планировщик остаётся в существующем процессе: новый API не запускает второго scheduler.

## 4. Экраны

### Расписание

- Сверху название выбранной группы и переключатель подписок; основная группа отмечена.
- Переключатель дат «Сегодня / Завтра / Послезавтра» с числом и днём недели; все три дня доступны сразу. По умолчанию открыт сегодняшний.
- Карточка пары: номер, предмет, преподаватель, кабинет. Время показывать только при наличии проверенного расписания звонков для этого источника.
- Обычная пара — нейтральная поверхность. Изменённая — янтарный фон и метка «Замена», «Другой кабинет» или «Другой преподаватель», раскрываемое «Было → Стало». Добавленная — отдельная метка. Отменённая — приглушённая карточка «Отменена», если отмена подтверждена.
- Цвет дублируется текстом и значком. При первом снимке без базы сравнения не помечать все пары как новые.
- Внизу дня источник и время обновления. Отдельные состояния: загрузка, нет подписки, расписание не опубликовано, подтверждённо нет пар, устаревшие данные, ошибка сети.
- Обновление при возврате в приложение, после изменения группы/настроек и по кнопке. Периодическая проверка только в видимом приложении; чтение не обращается к сайту для каждого пользователя.

### История

- Заголовок группы и недели: например, **«2–8 ноября 2026»**.
- Кнопки **«Предыдущая неделя»**, **«Следующая неделя»**, **«К последней неделе»**; быстрый выбор даты в календаре.
- Внутри недели прошедшие дни по убыванию даты. По состоянию на 4 ноября 2026 года первыми будут **«Вторник, 3 ноября 2026 года»** и **«Понедельник, 2 ноября 2026 года»**.
- День раскрывается в список итоговых пар с учётом последних известных замен. В текущей неделе не показывать будущие дни как пройденные; сегодня остаётся в «Расписании».
- По умолчанию открывается текущая неделя с прошедшими днями; в понедельник — предыдущая. Если данных нет, показать это и предложить переход к последней доступной неделе.
- Сохранять выбранную неделю, группу и позицию при переключении нижних вкладок; возвращать пользователя назад предсказуемо.
- Один результат на дату, а не несколько одинаковых дней из разных снимков. Для отсутствующих данных — «Расписание за этот день не сохранилось»; для подтверждённого пустого дня — «Пар не было».
- История — архив опубликованного расписания, а не подтверждение фактического проведения занятия или посещаемости.

### Профиль

- Имя, аватар при доступности, платформа запуска; блок связанных Telegram/VK с переходами в профиль.
- Подписки: список групп, выбор основной, добавление группы из существующего каталога, переключение и отписка от конкретной группы.
- Если пользователь отписывается от основной группы, предложить выбрать другую основную или остаться без основной. После отписки показывать актуальное состояние и в ботах.
- Настройки уведомлений: общий переключатель, выбор связанных каналов доставки и настройка для группы. Нельзя обещать доставку в заблокированный бот или без разрешения платформы.
- Оформление: системная / светлая / тёмная тема, акцент из небольшого набора, обычная / компактная плотность, уменьшение анимации. Системные ограничения доступности имеют приоритет.
- Существующий Telegram-стикер не переносить как VK-вложение. Предоставить отдельное платформенное действие, если сохранён текущий сценарий настройки стикера.
- Отписку подтверждать с названием группы и областью действия: после связывания изменение общее для аккаунта. Это подтверждение действия внутри продукта.

## 5. Общий аккаунт, несколько групп и совместимость

Предлагаемая модель — уточнить после проектирования миграций:

- `accounts`: внутренний ID и общие предпочтения.
- `account_identities`: связь аккаунта с существующим `(platform, user_id)`, уникальность этой пары. Одинаковые числовые ID Telegram и VK не означают одного человека.
- `account_subscriptions`: подписки на стабильные источники, основная подписка, подгруппа и настройки уведомлений. Предусмотреть переход `group-pending` в реальный источник без потери связи.
- `miniapp_preferences`: тема, акцент, плотность; допустимо объединить с настройками аккаунта.
- `account_link_requests`: хеш одноразового секрета, срок действия, инициатор, подтверждение обеих сторон и состояние использования.
- Короткоживущие серверные сессии миниаппа, отделённые от сессий админки.

Существующие `users` сохраняются. Их основную подписку можно временно поддерживать как совместимую проекцию общего аккаунта. Все записи подписок/настроек из Telegram, VK, админки и API должны проходить через единый сервис и транзакцию, иначе появятся два источника истины. Прямые изменения в иных местах выявить до миграции. Для старого бота команда выбора группы меняет основную подписку; дополнительные подписки миниаппа сохраняются до явной отписки.

Связывание: пользователь авторизован в первой платформе → создаёт одноразовую ссылку → открывает вторую платформу и проходит её проверенную авторизацию → видит оба профиля и возможные расхождения → явно подтверждает объединение. Секрет одноразовый, например на 5 минут; ограничить попытки и атомарно погашать его. При разных основных группах и настройках показать выбор. Не объединять по имени, аватару, username или числовому ID. Не переносить административные роли между платформами. Отвязка сохраняет платформенный профиль и его данные, отзывает затронутые сессии; правила разделения общих настроек описать и протестировать.

Общие предпочтения уведомлений и технический статус доставки разделить: блокировка Telegram не отключает VK. Обычное чтение профиля не должно автоматически снимать `delivery_disabled_auto`. Разрешения каналов получаются отдельными штатными действиями платформ.

Для нескольких групп расширить определение активных источников и выбор адресатов существующей рассылки. Проверить дедупликацию на уровне события, получателя и платформы; связывание аккаунтов не создаёт повторные сообщения одному получателю.

Существующие подписки на преподавателя, кабинет, вузовские недели и подгруппы должны продолжать работать. Если конкретный тип ещё не поддержан миниаппом, показать понятный переход в бот и предложить добавить группу, не переписывая старую подписку автоматически.

## 6. Архив и обратная совместимость при первом запуске

1. Добавить идемпотентную миграцию пользователей: каждому существующему платформенному профилю создать отдельный аккаунт и перенести его основную подписку и настройки. До добровольного связывания аккаунты не сливать.
2. Перед очисткой старых данных выполнить backfill из `schedule_snapshots`: разобрать дни в JSON, нормализовать источник и дату, выбрать последнюю допустимую версию **для каждого дня**. Более новый снимок, в котором нужного дня нет, не стирает этот день.
3. Снимки `daily_baseline` можно использовать как резерв при отсутствии более актуального принятого `current` для даты; порядок выбора должен учитывать фактическую свежесть и происхождение, а не только ID записи. Из событий изменений восстанавливать только те дни, для которых доказуемо есть полный состав, с указанием происхождения; текст сообщения сам по себе не считать полноценным расписанием.
4. Сохранять дневную запись с ключом `(source, date, week_variant)` там, где варианты действительно существуют. Подгруппы не схлопывать: хранить достаточные исходные данные для существующей фильтрации. Полезные поля: JSON пар, версия/хеш, revision ID источника, источник, `observed_at`, время импорта, состояние полноты.
5. Любое новое принятое расписание из сайта/ручного ввода/OCR обновляет проекцию дней через общий путь. Защита от пустого ответа сайта остаётся прежней. Явно подтверждённый пустой день сохраняется; отсутствующий день не превращается в отмену.
6. После завершения дня показывать последнюю принятую версию для этой даты. Более поздняя явная корректировка прошлого дня может обновить его итог с указанием времени исправления. Это не журнал всех промежуточных версий.
7. Диапазон UI: от `today - 3 календарных месяца` включительно до вчера включительно в `APP_TIMEZONE`; при вычитании месяца корректно ограничивать число последним днём месяца. При 4 ноября 2026 года начало — 4 августа 2026 года. Граничные недели обрезать по диапазону.
8. Очистку дневного архива привязать к датам занятий с запасом на календарные границы и восстановление, например хранить минимум 100 дней. Не увеличивать срок хранения всех технических журналов без необходимости. Backfill должен завершаться до удаления нужных ему исходных снимков; после сбоя безопасно продолжаться.
9. Backfill не изменяет счётчики пройденных пар, не повторяет рассылки, не очищает SQLite/JSON. Фиксировать прогресс, количество восстановленных дней и пропуски; для большой БД работать порциями.
10. Если состав дня никогда не сохранялся или уже удалён, показать пробел в архиве. Повторяющееся недельное расписание не выдавать за доказанное прошлое: оно не восстанавливает исчезнувшие замены. Гарантировать все прошлые пары можно только в пределах реально сохранившихся источников.

Для будущей истории источники должны продолжать собираться фоном, включая дополнительные подписки. Наличие календарных кнопок не означает, что за каждый день обязательно есть данные.

## 7. Структурированные замены

Сначала определить опорную версию для дня и время её фиксации. Хранить её отдельно от перемещаемого baseline рассылки, чтобы карточки не теряли отметку сразу после отправки уведомлений. Предлагаемое правило MVP: изменения текущего дня относительно первой принятой версии дня; для будущей даты — относительно первой известной версии этой даты. Явная коррекция опорной версии должна быть отдельным действием, а не побочным эффектом чтения.

Diff считает неизменные записи мультимножеством, затем сопоставляет остатки с учётом номера, источника, варианта недели и подгруппы. Нельзя использовать только `dict[number]`: в проекте допустимы одинаковые номера у разных пар. При неоднозначности показывать добавление/удаление или изменение дня без выдуманного соответствия «Было → Стало». Не объявлять переносом каждое исчезновение и появление похожего предмета.

Семантику существующих уведомлений сохранить. Полезно выделить общий структурированный diff и использовать его для UI, оставив текущие фильтры дат/отмен и форматирование сообщений. Если потребуется изменить правила уведомлений, оформить отдельное явное изменение с регрессионными тестами.

## 8. Черновой API

Префикс `/api/miniapp/v1`. Все пользовательские маршруты требуют сессию, кроме обмена проверенных параметров запуска на сессию.

| Метод и маршрут | Назначение |
| --- | --- |
| `POST /auth/telegram`, `POST /auth/vk` | Проверить подписанный запуск и выдать короткую сессию |
| `POST /auth/logout` | Отозвать сессию |
| `GET /me` | Профиль, связанные платформы, возможности и подписки |
| `PATCH /me/preferences` | Оформление и общие предпочтения |
| `GET /groups?query=…` | Поиск в существующем каталоге |
| `POST /me/subscriptions` | Добавить группу идемпотентно |
| `PATCH /me/subscriptions/{id}` | Основная группа, подгруппа, уведомления |
| `DELETE /me/subscriptions/{id}` | Отписаться от своей группы |
| `GET /schedule?subscription_id=…` | Три календарных дня, актуальность, статусы замен |
| `GET /history?subscription_id=…&week_start=YYYY-MM-DD` | Прошедшие дни недели, диапазон и предыдущая/следующая доступная страница |
| `POST /account-links`, `POST /account-links/confirm` | Начать и подтвердить связывание |
| `DELETE /me/identities/{platform}` | Отвязать дополнительную платформу после проверки условий |

`subscription_id` сервер проверяет на принадлежность аккаунту. Даты и границы истории вычисляет сервер. Добавить стабильную схему ошибок, номер ревизии и `updated_at`; после изменения подписки сбрасывать связанные query-кэши. GET-запросы не создают уведомлений и не меняют подписки. Действия записи логируются без секретов.

## 9. Авторизация и публикация

- Telegram: сервер проверяет исходную строку `initData`, подпись и допустимый возраст `auth_date`. `initDataUnsafe` не является доказательством личности.
- VK: сервер проверяет подписанные параметры запуска, ожидаемый app ID и свежесть запуска. Данные `VKWebAppGetUserInfo` подходят для отображения после авторизации, а не вместо проверки подписи.
- Для MVP — короткий Bearer-токен серверной сессии только в памяти фронтенда, с повторной авторизацией после истечения/перезапуска; без постоянного токена в localStorage. Проверить реальное поведение во встроенных браузерах. Если позже понадобятся cookie, отдельно спроектировать CSRF и iframe/cookie-ограничения.
- Не писать initData, query-параметры запуска, link-секреты или токены в access/error-логи и аналитику; убрать их из URL после обмена, когда это совместимо с маршрутизацией платформы. Задать ограничивающий Referrer-Policy.
- CSP, `frame-ancestors`, CORS и маршруты статики настроить именно для домена миниаппа и актуальных требований клиентов TG/VK. Не копировать запрет iframe из админки на VK Mini App и не ослаблять защиту админки.
- Боты открывают нужное приложение штатными кнопками. Добавление кнопок не удаляет полезные существующие клавиатуры и fallback-переходы.
- Настройка Telegram-приложения, VK app ID, секретов и HTTPS выполняется на этапе интеграции; для написания плана реальные токены не нужны.

## 10. Этапы реализации и критерии выхода

| Этап | Результат | Критерий готовности |
| --- | --- | --- |
| 1. Контракты и аудит | Карта всех чтений/записей подписок, DTO, правила истории/diff, черновики трёх экранов | Есть примеры пустого дня, замены, нескольких групп, старого пользователя и конфликта связывания |
| 2. Архив и миграция | Дневной архив, backfill, индексы, независимое хранение | Старая тестовая БД сразу отдаёт прошлые дни; повторный запуск ничего не дублирует и не рассылает |
| 3. Общие аккаунты | Несколько подписок, совместимость `users`, единый сервис записи и рассылки | Изменение в любом боте видно в API и наоборот; дополнительные группы получают корректные уведомления |
| 4. Авторизация и API | Telegram/VK-проверки, сессии, профиль, расписание, история, настройки | Нельзя подделать пользователя или изменить чужую подписку; API читает общие данные |
| 5. React-оболочка | Нижняя навигация, адаптеры, темы, состояния загрузки/ошибок | Корректны safe area и «Назад» в обоих клиентах; контент не перекрыт нижним меню |
| 6. Расписание | Три дня, переключатель групп, структурированные замены | Данные совпадают с ботом при одинаковом источнике, дате и подгруппе; замена остаётся видимой после рассылки |
| 7. История | Недели, календарь, раскрытие дней, восстановленные записи | Навигация показывает точные даты; на первом запуске видны доступные старые дни; нет дублей версий |
| 8. Профиль и связывание | Настройки, подписки, одноразовое связывание/отвязка | После явного объединения настройки общие; роли и ограничения доставки не переносятся ошибочно |
| 9. Деплой и приёмка | Frontend build, отдельный API, nginx/HTTPS, CI, инструкции | Полный pipeline зелёный и проведён smoke в реальных Telegram/VK; админка работает по прежним правилам |

Этапы 2–4 образуют основу; рабочий MVP включает все три вкладки, дополнительные подписки, backfill и добровольное связывание. Отдельным развитием оставить новые виды уведомлений, напоминания перед парами, журнал всех версий, расширенную аналитику и сложную анимацию. Срок оценивать после этапа 1 и проверки реальных данных архива.

## 11. Обязательные проверки

- Старые и свежие БД, повторная миграция, несколько подписок, сохранение групп/подгрупп/настроек, `group-pending`, изменение из каждого канала, конкурентные записи.
- Backfill: несколько версий в день, отсутствие дня в новом снимке, подтверждённая отмена, ложный пустой ответ сайта, поздняя корректировка, разные варианты недели, границы месяца/года, диапазон трёх календарных месяцев.
- Архивирование при повторной доставке задачи, рестарте и сбое посередине backfill; отсутствие повторного подсчёта пар и рассылок.
- Diff: кабинет, преподаватель, предмет, добавление/отмена, одинаковые номера, неоднозначное сопоставление, отсутствие опорной версии, обновление baseline после рассылки.
- Авторизация: неверная/просроченная подпись, неверный app ID, одинаковые ID на разных платформах, отозванная сессия, чужая подписка, повторное использование link-секрета и конфликты аккаунтов.
- Доставка: общие предпочтения и раздельные ограничения каналов, дедупликация, сохранение кнопок Telegram/VK и fallback-сценариев.
- UI: русские даты, нижнее меню и safe area, светлая/тёмная тема, доступные контрасты, области нажатия от 44×44, reduced motion, ширина от 320 px, история и переходы назад, потеря сети.
- Для backend-логики добавить тесты в `tests/`; для React — Vitest/Testing Library на пользовательские состояния и Playwright на ключевые сквозные сценарии. Моки платформ не заменяют smoke в реальных клиентах.

Обязательный pipeline перед каждым коммитом реализации:

```powershell
uv run --frozen ruff check src web_configurator tests scripts --output-format=github
uv run --frozen python -m compileall -q src web_configurator tests scripts
uv run --frozen python -m unittest discover -s tests -p "test_*.py" -v
```

Когда появится `miniapp_api/`, включить его в линтер и compileall, настроить frontend typecheck/test/build в CI. После изменения деплоя проверить `docker compose config`. Обновить README, `.env.example`, backup/restore и инструкцию первого запуска с backfill. Нужные секреты хранить только на сервере. Feature flags и возврат к старым ботам при проблеме не должны требовать удаления новых таблиц или данных.
